# 冷启动分析

将冷启动视为一种延迟场景，其确切的完成语义可能因应用而异。在结构化结果中填写 `cold_start`。不要求提供业务标记或用户提供的进程，但当提供了可靠的应用定义时应予以尊重。

## 确定目标进程

1. 在 `get_trace_overview` 之后调用一次 `inspect_cold_start_candidates`。传入 `target_process` 或空字符串，并使用较小的候选数量上限。
2. 将 `target_process` 视为可选提示。根据 Trace 事实对其进行验证。
3. 将返回的进程、主线程、实际的 `app_startup` 行、最早的 Slice 以及首帧作为候选，而非决策。不要假设固定的 Marker 词汇表。
4. 优先选择在 Trace 内创建的、具有连续的生命周期到帧链的进程。排除系统守护进程和长生命周期进程。
5. 记录选定的 `pid`、`ipid`、主 `tid`/`itid`、原因、置信度、证据以及可信的备选方案。
6. 如果候选仍然模糊不清，仅使用最强候选继续，降低置信度，并报告模糊性。
7. 选定 `ipid` 后，调用一次 `inspect_cold_start_timeline`。开始时使用 3 秒回溯、5 秒前瞻的有限窗口，最多 160 个事件。不要为初始发现请求 500 个事件的最大值。仅当返回的证据表明可信边界在结果之外时，才扩展窗口或事件数量。
8. 将返回的锚点、事件、阶段、帧链接和 `boundary_evidence` 视为结构化事实。工具的 `metric_candidate` 是确定性的平台指标候选，而非输入因果关系的证明或场景决策的替代品。当该候选中的任何链接模糊不清时，使用 `query_trace_sql` 进行有针对性的跟进。
9. 保持调查范围有限。在概览、候选和时间线发现之后，使用不超过 12 次有针对性的 SQL 调用。使用 CTE、条件聚合或 `UNION ALL` 合并阶段比较；不要通过重复的试探性查询探测相同的模式或条件。（）

## 确定冷启动边界

1. 证明目标进程未被复用。排除温启动或热启动。当 `process.start_ts` 缺失时，仅将时间线的回退锚点用于发现，并且在声称冷启动之前需要生命周期/进程生成证据。
2. 当 `app_startup` 有行时，阅读 `references/smartperf-app-startup.md`。将这些行视为解析器产生的强证据，按解析出的包名过滤，并保留原始标识符。启动链可以跨进程和线程。
3. 当 `app_startup` 为空时，使用 `query_trace_sql` 检查此 Trace 中实际的生命周期和渲染 Slice。不要合成 SmartPerf 阶段标签，或盲目匹配另一个 Trace 中的示例 Marker 名称。
4. 在没有独立证据的情况下，不要将最早的 `app_startup.start_time` 视为启动边界，或将最晚的 `end_time` 视为首帧。
5. 选择最强的可观察启动请求或进程创建边界。当 `boundary_evidence.metric_candidate.status` 为 `proven_platform_boundary_pair` 时，使用其平台启动标记作为标准化的 `start_boundary`；不要默默地用更早的进程时间戳替代。不同的指标必须明确标注，且不得替换此标准化持续时间。
6. 不要仅仅因为最早的 `frame_slice` 行在时间上最先就将其用作冷启动完成点。首先确定此应用的指标定义。它可能是第一个主线程 Actual 帧、一个后续的证明首页已进入且稳定的帧，或一个唯一标识的应用完成 Slice。
7. 当指标定义为应用帧时，要求选定的主线程 `ReceiveVsync` 拥有预期的 Actual 帧，并通过 `frame_maps` 链接到渲染服务帧。记录为什么此帧满足应用的启动语义。当提供了唯一的应用 Slice 对时，将两个 Slice 时间戳用作问题区间，并将任何技术性的首帧指标分开保存。
8. 同时将映射的渲染服务帧结束记录为 `presentation_boundary`。从相同的 `start_boundary` 到 `presentation_boundary` 计算 `presentation_duration_ms`；它不是渲染阶段的持续时间。将此指标与选定的应用完成边界区分开。当选定的完成点是后续的应用标记或稳定首页边界时，标准化的技术首帧呈现可能合法地先于它；不要将呈现时间戳强制推到应用定义区间的末尾。
9. 仅当触摸/点击事件与启动之间存在经过证明的因果链时，才将指标称为点击到帧。仅时间上的接近是不够的。
10. 记录所有选定边界的确切时间戳、来源、置信度、指标语义和证据。
11. 如果任一必需的边界不可靠，报告候选边界，不要声称已确认的冷启动持续时间或根因。

## 构建关键路径

1. 测量精确的边界到边界持续时间。
2. 仅划分由 Trace 事实支持的阶段：进程创建、运行时初始化、应用生命周期、页面构建、首帧渲染和呈现。优先使用实际有效的 `app_startup` 行作为阶段候选，但根据 Slice 验证其标签和边界。永远不要凭空捏造缺失的行，或将对表格缺失或为空的 Trace 强制套用参考阶段列表。
3. 将阶段保持在冷启动区间内，避免重复计算嵌套或重叠的 `app_startup`/Slice 范围。`cold_start.stages` 必须在选定的 `end_boundary` 处或之前结束。不要将阶段扩展到 `presentation_boundary`；改为在摘要中描述短暂的应用到 RS 呈现尾部。
4. 识别在总延迟或同类基线回归中占主导地位的阶段。
5. 识别控制阶段完成的线程或依赖链。
6. 对于每个主导阶段，应用 `.qoder/skills/trace-analysis/references/thread-execution-critical-path.md` 中的通用方法，并分析：
   - 实际 CPU 运行时间，而非 Slice 墙钟时间；
   - 可运行延迟和同期的 CPU 竞争者；
   - CPU 分布、迁移和原始优先级观察；
   - 睡眠或不可中断等待及其因果唤醒链；
   - 跨进程 IPC、I/O、任务队列和渲染依赖。
   首先分析主导阶段和整个启动窗口。不要仅为填充可选字段而对每个次要阶段发出单独的 CPU 分布查询。当需要线程证据时，使用精确的阶段边界调用 `inspect_thread_execution`，但不要将其模型就绪的值复制到 Agent 草稿中。应用层在提交后注入支持的阶段线程。
7. 当存在基线时，比较等效的边界和阶段。
8. 当建议将 SO 或模块延迟加载或从启动路径中移除时，列举支持该建议的具体启动窗口 Slice 观察。按合并的每模块墙钟区间排序模块，保留标记类型和路径，并在路径允许时区分应用模块和平台模块。声明不同模块可能嵌套，因此不能求和，并且不要将此墙钟区间描述为 CPU 运行时间。

## 防护规则

- 将每个状态和 Slice 区间裁剪到阶段窗口内。
- 不要对嵌套的 Slice 墙钟持续时间求和。
- 不要在没有与 `Running` 区间相交的情况下将长墙钟 Slice 标记为 CPU 工作。
- 不要在没有证明进度等待其唤醒的情况下将 `S` 标记为阻塞者。
- 不要仅凭 CPU 迁移或集中本身就将其标记为有害。
- 当 Trace 未暴露时，不要推断大/小 CPU 类别、频率、亲和性、RTG 或调度器策略。
- 不要仅凭优先级值就声明调度不合理。
- 保留原始优先级值；仅在平台语义已确定时解释其顺序。

## 输出要求

- 填写 `cold_start.resolved_process`、启动和选定的应用定义完成边界、总持续时间、语义阶段和证据 ID。不要序列化 `critical_threads` 或 `perf`；确定性注入在提交后添加这些大型结构。当存在应用到渲染服务映射时，同时填写 `presentation_boundary` 和 `presentation_duration_ms`。
- 区分总启动回归和阶段级回归。
- 保持阶段、线程状态、CPU 分布、唤醒和竞争证据可独立追溯。
- 推荐使用相同的采集条件进行可测量的冷启动复测。
- 当仅有文件元数据可用时，停止而不给出根因发现。
