
可以。现在我给你**最终定版**，后面就不要再反复改方向了。

结合你当前的 **Trace Agent + Qoder Agent Runtime + `AgentTransport` + ToolRegistry + SQLite Trace + Memory + Latency Control**，以及 2026 年成熟 Agent Eval 的做法，我建议你把 Eval 做成一个**独立于生产 Agent 的评测层**。Anthropic 目前公开的定义就是 `task → trial → transcript → outcome → grader → evaluation harness → suite`，并明确建议生产 Agent 与被评测 Agent 尽量一致、Trial 隔离、代码评分优先、LLM Judge 辅助；OpenAI 近期也明确强调，Agent 的评测结果受到 harness、工具、上下文管理、重试和评分方式影响，因此 harness 本身就是评测的一部分。([Anthropic][1])

另外，OpenAI 已宣布 2026 年 11 月 30 日后关闭原 Evals/Agent Builder 产品，所以你的项目**不要依赖某一家厂商的 Eval 平台**，自己做轻量、模型无关的 Eval Core 是更稳妥的选择。([OpenAI][2])

## 一、先定死一个原则

**Eval System 不允许自己实现 Agent。**

它只能：

```text
加载 Case
→ 准备环境
→ 调用 Production Agent
→ 捕获 Trial
→ Grading
→ 聚合
```

也就是说：

```text
Production:
CLI → AnalyzeApplication → AgentRuntime → QoderTransport

Eval:
EvalHarness → AnalyzeApplication → AgentRuntime → QoderTransport
```

而不是：

```text
EvalHarness → 自己重新写一套 Qoder 调用逻辑
```

这个边界非常重要。否则以后 Production Agent 改了，Eval Agent 还是旧的，测出来的结果没有意义。Anthropic 也明确建议 eval 中的 Agent 与实际生产 Agent 尽可能保持一致。([Anthropic][1])

# 六、Grader 第一版只做 Deterministic

第一版**不要急着上 LLM Judge**。

```text
check_root_cause()
```

例如：


然后做 Partial Credit。

Anthropic 当前实践同样明确推荐：能代码判断的优先用代码评分，多组件任务使用 partial credit，复杂主观维度再引入 LLM Judge。([Anthropic][1])

# 七、测试内容最终分成 3 层，而不是一锅端

这是你之前一直问的“到底测什么”，现在可以正式敲定。

## 第一层：Framework Tests

**目标：证明你的 Eval Framework 没有 Bug。**

先做大约 10 个人工构造 Case：

```text
F01 Case 正确加载
F02 Gold 正确加载
F03 Trial 隔离
F04 Artifact 正确保存
F05 Agent 成功运行
F06 Agent Timeout
F07 Tool Error
F08 Agent Crash
F09 非法 Structured Output
F10 Grader Partial Credit 正确
```

这里不用真实复杂 Trace。

它测的是：

> **“我的评测系统能不能可靠地测？”**

---

# 八、第二层：Agent Capability Tests

这才是真正测试你的 Trace Agent。

第一批建议 **10～20 个真实 Trace**。

必须覆盖：

```text
01 CPU contention
02 Thread blocking
03 Binder / IPC
04 UI scheduling
05 VSync
06 RenderService
07 单一明显瓶颈
08 多候选瓶颈
09 多因素竞争
10 证据不足
11 证据冲突
12 表面现象与真正根因分离
```

这批的目的不是追求 100%。

而是找：

```text
Agent 到底会在哪类问题上失败
```

Capability Eval 本来就应该放在 Agent 当前能力边界上，而不是全放简单题。([Anthropic][1])

---

# 九、第三层：Regression Tests

以后生产环境发现：

```text
Agent 某次分析错了
```

不要只修 Prompt。

直接：

```text
Production Failure
       ↓
Create Eval Case
       ↓
加入 regression/
       ↓
以后每次自动跑
```

这就是你的核心飞轮：

```text
生产失败
   ↓
Eval Case
   ↓
修 Agent
   ↓
Regression
   ↓
验证修复
   ↓
继续生产
```

Regression 的目标接近：

```text
100%
```

因为它测试的是：

> **过去已经掌握的能力有没有退化。**

Anthropic 也是把 capability eval 最终毕业成 regression suite，并持续运行。([Anthropic][1])

# 十一、第二阶段再加 LLM Judge

等 Deterministic Grader 跑稳之后再加：

```text
LLM Judge
```

只负责：

```text
Causal Reasoning
Evidence Sufficiency
Reasoning Quality
Uncertainty
Report Quality
```

不要让它重新判断：

```text
metric 是不是 1250
event 到底有没有
root cause 是否命中明确枚举
```

这些交给代码。

LLM Judge 最终应该输出：

```json
{
  "reasoning": 0.82,
  "evidence_quality": 0.91,
  "uncertainty": 0.75,
  "report_quality": 0.88
}
```

而且后面一定做：

```text
LLM Judge
    ↕
Human Calibration
```

因为模型评分本身也需要验证；Anthropic 明确强调 LLM Judge 必须持续与人工判断校准。([Anthropic][1])

# 十二、评分最终就采用这一套

第一版：

```text
Diagnosis          35%
Evidence           25%
Metrics            15%
Reasoning          10%
Uncertainty         5%
Report              5%
Efficiency          5%
```

但是系统内部**不要只保存一个 Final Score**。

保存：

```text
overall
diagnosis
evidence
metrics
reasoning
uncertainty
report
efficiency
```

这样才能知道：

```text
总体提升
≠
根因识别提升
```

# 十三、不要把 Tool Sequence 当核心指标

记录：

```text
tool calls
```

但不要要求：

```text
必须：
A → B → C → D
```

因为一个优秀 Agent 可能：

```text
A → C → D
```

一样能找到正确答案。

成熟 Agent Eval 更应该评估 **outcome + evidence + quality**，而不是死卡执行路径。Anthropic 对此明确提出不要过度规定工具调用顺序。([Anthropic][1])

Tool Call 更适合用于：

```text
效率分析
异常诊断
工具使用错误
Agent 行为研究
```

这套方案的核心思想就是：

> **先把“评测基础设施”做可靠，再把“Agent 能力评测”做丰富。**

这样你现在正在建设的 Runtime、`QoderTransport`、ToolRegistry、Memory、Latency Control 都不会被 Eval 绑死；Eval 只是通过稳定的 Production Agent 入口观察它们的整体行为。这也符合当前成熟 Agent Eval 的方向：**评估的是 Agent + Harness + Tools + Environment + Outcome 的整体系统，而不是单纯 LLM 最后一段回答。** ([Anthropic][1])

**所以你下一步最具体的开发任务，就是：先建立 `src/trace_agent/eval/`，把上述 6 个 Contract 和一个 `cold_start_001` 最小 Case 跑通。**
